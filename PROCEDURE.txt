NOVAFIT - BONS D'INTERVENTION - PROCÉDURE COMPLÈTE (sauvegarde du 10/11/2026)
================================================================

COMPTES PERSONNELS ET DROITS (version du 12/11/2026)
  Chaque personne a son propre code. Les droits se cochent un par un (page « Utilisateurs » de l'accueil, administrateur seulement) :
    Jonction | Intervention (bons vierges et de commande) | Non-conformités | Achats | Gestion (Interventions finies) |
    Fournisseurs (annuaire par tags) | Administrateur (tous les droits + gestion des comptes + modification des lignes Jonction/bons)
  Données : Google Sheet « Utilisateurs Novafit » (créé automatiquement), onglets Utilisateurs (nom, code, actif, une case par droit)
  et Appareils. ATTENTION : ce Sheet contient les codes en clair : ne le partager avec personne.
  Départ d'une personne : décocher « Compte actif » (page Utilisateurs ou Sheet). Effet en moins d'une minute, sur tous ses appareils.
  Code : généré par le script (prénom + 6 chiffres), modifiable, minimum 6 caractères, unique. Blocage après plusieurs échecs (déjà en place).
  Appareils : à chaque connexion l'appli envoie un identifiant d'appareil (aléatoire, gardé dans le navigateur). Le script n'écrit une
  ligne que pour un appareil NOUVEAU de cette personne. Le 1er appareil est validé d'office ; les suivants passent « Nouveau » et le
  voyant « Utilisateurs » de l'accueil devient orange jusqu'au clic sur « C'est bon » (ou Supprimer). Aucun blocage.
  Limite : un navigateur vidé ou un autre navigateur = nouvel appareil, sans que ce soit une fraude.
  Jonction : la page Jonction parle directement au script Jonction avec ses codes communs. Pour les comptes personnels, le script
  donne ces codes à l'appareil de la personne selon ses droits, depuis deux propriétés du script des bons :
    JONCTION_CODE_ACCES = valeur de CODE_ACCES du script Jonction     (droit Jonction)
    JONCTION_CODE_ADMIN = valeur de CODE_ADMIN du script Jonction     (droit Administrateur)
  Limite à connaître : quelqu'un qui a eu le droit Jonction garde ces codes sur son téléphone. Au départ d'une personne, changer
  CODE_ACCES dans le script Jonction ET la propriété JONCTION_CODE_ACCES ; les autres se reconnectent une fois pour le récupérer.
  Transition : LOGIN_ANCIEN = true (haut de Code.gs) laisse marcher les anciens codes communs (technicien/gestionnaire/admin).
  Quand tous ont leur code personnel : LOGIN_ANCIEN = false puis nouvelle version du déploiement.

MISE EN SERVICE DES COMPTES (dans cet ordre)
  1. Coller le nouveau Code.gs dans l'Apps Script du Sheet Bons ; exécuter initialiserUtilisateurs() (une autorisation peut être demandée).
     Cela crée le Sheet « Utilisateurs Novafit » avec un premier compte administrateur « Willy » et son code (à lire dans le Sheet).
  2. Propriétés du script : ajouter JONCTION_CODE_ACCES et JONCTION_CODE_ADMIN (voir ci-dessus).
  3. Déployer > Gérer les déploiements > Modifier > Nouvelle version.
  4. Envoyer les fichiers du dossier 1_GitHub sur GitHub (nouveaux : fournisseurs.html, utilisateurs.html), recharger deux fois.
     Toutes les connexions en cours sont fermées : tout le monde se reconnecte une fois.
  5. Se connecter (ancien code ou code de Willy), ouvrir Utilisateurs, créer les comptes, transmettre les codes.
  6. Quand tout le monde est passé aux codes personnels : LOGIN_ANCIEN = false, nouvelle version.

NOM DE LA PERSONNE QUI SAISIT
  - Accueil : « Connecté : Prénom Nom » (comptes personnels). Les anciens codes communs affichent seulement le niveau.
  - Achats : la colonne « Saisi par » du Sheet (colonne I) reçoit le nom du compte ; la liste affiche « par … » sous le numéro.
  - NC : une colonne « Saisi par » est ajoutée dans chaque onglet, juste après ta dernière colonne (titre créé s'il est vide ;
    vérifier qu'elle ne tombe pas sur une colonne déjà utilisée dans ton fichier). Affichée dans la liste des NC.
  - Bon d'intervention : le technicien du même nom (prénom/nom dans n'importe quel ordre) est coché d'office, modifiable.
  - Avec un ancien code commun, la colonne indique « Code commun gestionnaire » (ou technicien/admin).

APERÇU DES ACHATS AVANT ENVOI
  Le bouton du formulaire est « Prévisualiser la commande » : le PDF s'affiche sans rien enregistrer, sans consommer de numéro et sans
  envoyer de mail. Deux choix : « Retour » (la saisie est conservée) ou « Envoyer la commande » (enregistrement, numéro attribué, mail).
  Le numéro affiché est celui qui sera attribué (une seule personne saisit les commandes).

ANNUAIRE DES FOURNISSEURS PAR TAGS (droit Fournisseurs ; suppression et renommage de tags = administrateur)
  Sheet « Annuaire fournisseurs Novafit » (créé automatiquement), onglet Fournisseurs, colonnes : Fournisseur | Familles | Tags |
  Contacts | Téléphones | Emails | Notes. Familles et tags séparés par « ; » ; contacts, téléphones, emails : un par ligne dans la cellule.
  Onglet Tags : tags créés à l'avance. Un ancien Sheet (colonnes Métier/Type/...) est converti automatiquement à la première ouverture.
  IMPORT : ouvrir Import_fournisseurs.xlsx (108 fournisseurs issus de l'Excel d'origine), tout sélectionner (en-têtes compris), copier,
  puis coller en A1 de l'onglet Fournisseurs du Sheet annuaire (avant tout, le Sheet doit être vide ou on remplace son contenu).
  Page Fournisseurs : vue Fiches ou Tableau (choix mémorisé), recherche multi-mots tolérante aux fautes, familles en boutons, nuage de tags
  (+ Nouveau tag, Gérer les tags = renommer/fusionner partout), bouton Modifier sur chaque fournisseur (familles, tags avec propositions,
  plusieurs contacts/téléphones/emails, notes, suppression admin), + Nouveau fournisseur. Hors ligne : modifications gardées puis envoyées.
  Aucun lien avec la liste de fournisseurs des Achats (consommables). Code.gs à redéployer (nouvelle version).

ÉTAPE 1 - Jonction (nouveau compte Gmail)
  1. Dupliquer le Google Sheet Jonction dans le nouveau compte (Fichier > Créer une copie), avec son Apps Script.
  2. Dans l'Apps Script Jonction : appliquer patch-jonction.txt (ajoute CODE_GESTIONNAIRE et le nouveau doGet).
     Renseigner vos 3 codes. Les codes que vous avez collés dans le chat sont à changer.
  3. Déployer > Nouveau déploiement > Application Web : exécuter en tant que MOI, accès : tout le monde.
     Copier l'URL /exec  => URL_JONCTION.

ÉTAPE 2 - Google Sheet "Bons d'intervention"
  Onglet "Bons", ligne 1 (14 colonnes A à N) : N° de BL | N° de commande | Date d'intervention | Client | Email client |
     Nom du signataire | Technicien | Matière | Largeur | Longueur | Commentaire (bande) | Commentaire intervention |
     Heure de début | Heure de fin
     (Si des bons existent déjà : insérer la colonne F "Nom du signataire" AVANT d'utiliser la nouvelle version.)
  Onglet "Techniciens" : noms en colonne A à partir de la ligne 2.
  Onglet "Config" : A1 = compteur, B1 = 0.
  Ne PAS partager ce Sheet publiquement.

ÉTAPE 3 - Google Drive
  - Créer le dossier "Commande en cours" (nom unique) et y déposer les PDF nommés "N° commande - Client.pdf"
    (ex : 12345 - Dupont SA.pdf).
  - Les dossiers "Intervention faite" (commandes traitées) et "Bons d'intervention" (PDF de chaque bon,
    nommé "BI-2026-0001 - Client.pdf") sont créés automatiquement à côté.
  - Déposer le logo dans Drive, noter son ID => LOGO_DRIVE_ID.

ÉTAPE 4 - Apps Script des bons (Extensions > Apps Script du Sheet Bons)
  1. Coller Code.gs. Régler les constantes en haut : EMAIL_ENTREPRISE, NOM_ENTREPRISE, EMAIL_EXPEDITEUR,
     MODE_ENVOI ('graph' = envoi depuis info@novafit.fr via Microsoft 365, mode en service ; 'gmail' = envoi depuis le compte Gmail),
     LOGO_DRIVE_ID, URL_JONCTION (étape 1), AGENCES.
  2. Exécuter une fois la fonction autoriser() et accepter les autorisations.
  3. Déployer > Nouveau déploiement > Application Web : exécuter en tant que MOI, accès : tout le monde.
     Copier l'URL /exec  => URL_API.
  4. À chaque modification du script : Déployer > Gérer > Modifier > Nouvelle version.

ÉTAPE 5 - GitHub (dépôt Intervention)
  1. Éditer config.js : remplacer les deux URL (URL_API, URL_JONCTION) par celles des étapes 1 et 4.
  2. Supprimer l'ancien bons.html, puis déposer : index.html, nc.html, nc-ajout.html, intervention.html, jonction.html, commandes.html,
     termines.html, commun.js, commun.css, theme.js, theme.css, shell.js, shell.css, config.js, manifest.webmanifest, sw.js, icon-192.png, icon-512.png.
  3. Attendre 1-2 min (GitHub Pages), recharger la page ; sur téléphone fermer/rouvrir l'application
     (cache novafit-v18).

AFFICHAGE
  Toutes les pages ont le même en-tête (actualiser, bouton clair/sombre) et une barre d'onglets en bas :
  Accueil / Jonction / Vierge / Commande / Finies (onglets grisés + cadenas si le niveau est insuffisant).
  Accueil : indicateurs (interventions à réaliser ; bons en attente d'envoi, case jaune sur laquelle on appuie pour renvoyer).
  Le bouton clair/sombre (en-tête) est enregistré dans le navigateur (ou l'app) de
  chaque appareil uniquement et s'applique à toutes les pages, Jonction comprise.

FONCTIONNEMENT
  Le client du bon est repris du nom du PDF : tout ce qui suit le premier tiret ("CD260123 - Dupont" ou "CD260123-Dupont").
  Le bon demande le nom du signataire (au-dessus de la signature), enregistré en colonne F et imprimé sur le PDF.
  Accueil : Jonction / Bon d'intervention (sans commande) / Commandes en cours / Interventions finies.
  Commandes en cours : liste des PDF > clic = document avec "← Retour" et "Faire le bon d'intervention"
     (client et N° de commande préremplis). À l'envoi : mails entreprise + client, PDF déplacé vers
     "Intervention faite". Hors ligne : le bon est mis en file et envoyé au retour du réseau.
  Interventions finies : recherche (BL, commande, client, dates), bouton PDF de la commande ; l'administrateur
     peut modifier les lignes (changer le N° de commande ne renomme pas le PDF).

ENVOI DES MAILS VIA MICROSOFT 365 (MODE_ENVOI = 'graph') - EN SERVICE DEPUIS LE 10/11/2026
  Pourquoi : les mails envoyés depuis Gmail n'arrivaient pas sur les adresses @novafit.fr. Le script envoie maintenant
  depuis la boîte partagée info@novafit.fr via Microsoft Graph (mails internes, copie dans les éléments envoyés d'info@).
  Côté Azure (fait par le prestataire/administrateur) :
    1. Entra ID > Inscriptions d'applications > nouvelle application, locataire unique.
    2. Autorisations d'API > Microsoft Graph > Autorisations de l'application > Mail.Send + consentement administrateur.
    3. Certificats et secrets > nouveau secret client (copier la VALEUR, pas l'ID du secret). Expiration : 10/11/2028.
    4. Limiter l'application à la seule boîte info@novafit.fr (Application Access Policy ou RBAC pour les applications).
    5. Transmettre : ID de l'annuaire (locataire), ID d'application (client), valeur du secret (canal privé).
  Côté Apps Script (Paramètres du projet > Propriétés du script) : ajouter 3 propriétés, noms exacts :
    GRAPH_TENANT_ID, GRAPH_CLIENT_ID, GRAPH_CLIENT_SECRET   (les valeurs ne sont PAS écrites dans ce document).
  Puis : MODE_ENVOI = 'graph' dans Code.gs, enregistrer, Déployer > Gérer > Nouvelle version, lancer testerMail,
  vérifier l'onglet Journal du Sheet.
  Les valeurs des 3 propriétés sont à retrouver auprès de l'administrateur Azure (ou dans votre gestionnaire de mots de passe).
  Si tout est perdu : l'administrateur crée un nouveau secret (5 minutes) et vous le recollez dans GRAPH_CLIENT_SECRET.
  RENOUVELLEMENT DU SECRET : expire le 10/11/2028. Rappel à mettre début octobre 2028. On ne recrée pas l'application :
  l'administrateur ajoute un nouveau secret AVANT l'expiration de l'ancien, vous remplacez GRAPH_CLIENT_SECRET, aucune coupure.
  Retour au mode Gmail si besoin : MODE_ENVOI = 'gmail' puis nouvelle version.
  Dépannage (colonne Résultat du Journal) : invalid_client / AADSTS7000215 = mauvaise valeur de secret ; AADSTS700016 ou
  AADSTS90002 = ID erroné ; 403 = consentement ou stratégie d'accès ; 404 = adresse expéditrice ; 429 = trop d'envois.

RÉSEAU FAIBLE ET ENVOI DU BON (version du 10/11/2026)
  - Le site s'ouvre à partir de la copie enregistrée sur l'appareil (instantané, même avec une barre de réseau) et se met à jour en
    arrière-plan : une nouvelle version déposée sur GitHub est donc prise en compte à la 2e ouverture (fermer/rouvrir l'application).
  - Les appels au script ont un délai maximum (10 à 15 s ; 45 s pour l'ouverture d'un PDF). Passé ce délai, l'écran affiche les
    dernières données enregistrées (liste des commandes, compteur) au lieu de rester bloqué.
  - Validation d'un bon : il est d'abord gardé sur l'appareil, puis envoyé (20 s maximum). Dans tous les cas on revient à l'ACCUEIL :
    message vert « Envoi validé : bon BI-… » si l'envoi a réussi ; message jaune « Bon enregistré, il partira dès que le réseau le
    permet » et la case jaune « Bon en attente d'envoi » affiche 1. Appuyer sur cette case renvoie le bon (sans doublon : le script
    reconnaît le bon par son identifiant d'envoi).
  - Limite : l'ouverture d'un PDF de commande demande du réseau (le lecteur PDF est gardé sur l'appareil après la 1re utilisation).

NON-CONFORMITÉS (gestionnaire et administrateur uniquement)
  Accueil : 6 cartes (NC fournisseur / fabrication / commande, chacune en total et sur 30 jours) + bouton « Ajouter une NC ».
  Un appui sur une carte ouvre la liste (nc.html) déjà filtrée ; on peut y changer type, dates, état du dossier et recherche.
  Les techniciens ne voient ni cartes ni bouton, et le script refuse leurs demandes.
  Données : Google Sheet « Non-conformités Novafit », créé automatiquement au premier usage (son ID est gardé dans la propriété
  du script NC_SHEET_ID). Onglets : NC Fabrication, NC Fournisseur, NC Magasin (= type « commande »).
  Pour utiliser un Sheet existant : renseigner son ID dans la constante NC_SHEET_ID de Code.gs (3 onglets aux noms ci-dessus,
  mêmes colonnes dans le même ordre, colonne A = date de réclamation).
  Colonnes : Fabrication = Date de réclamation, Client, Commande, Code et Désignation article Non-conforme, OF, Non-conformité,
  Action, OF NC, Clôture Dossier. Fournisseur = Date, Fournisseur, Commande, Nom Client, puis Code..., OF, Non-conformité, Action,
  OF NC, Clôture Dossier. Magasin = comme Fabrication.
  « 30 derniers jours » = date de réclamation ; « Clôturé » = la colonne Clôture Dossier est remplie (une date).
  Changer les champs : tableau NC_TYPES en bas de Code.gs (le formulaire s'adapte tout seul).
  Mise en service : coller Code.gs, exécuter autoriser() (nouvelle autorisation Sheets), nouvelle version du déploiement.

ACHATS FOURNISSEURS (gestionnaire et administrateur uniquement)
  Pages : achats.html (liste) et achat-nouveau.html (formulaire). Aucun bouton ni page pour le technicien ; le serveur le refuse aussi.
  Données : Google Sheet « Achats Novafit », créé automatiquement au premier usage (ID gardé dans la propriété ACHATS_SHEET_ID).
  Onglets : Commandes (A-F = FOURNISSEUR, Date Cde, N° Commande, Description, MONTANT HT, RECUE ; G-N = suivi), Fournisseurs
  (Fournisseur, Email, Contact ; s'enrichit à chaque commande), Config (B1 = dernier numéro utilisé).
  Numérotation : « ATELIER 26-0084 » puis 26-0085... (26 = année, 4 chiffres = compteur). Le 1er janvier le compteur repart :
  ATELIER 27-0001. Onglet Config du Sheet Achats : B1 = dernier numéro de l'année, B2 = année de ce numéro (remplie toute seule).
  Pour corriger le compteur à la main : mettre le dernier numéro réellement utilisé en B1 (et l'année en B2 si elle est vide ou fausse).
  Constantes : ACHATS_PREFIXE (ATELIER), ACHATS_PREMIER_NUMERO (84, utilisé seulement si Config est vide).
  PDF : enregistré dans le dossier Drive « Commandes fournisseurs » (« NUMERO - Fournisseur.pdf »), visible par bouton « Commande ».

  logo intégré ; il reste dans les éléments envoyés de cette boîte. Objet et message pré-remplis, modifiables.
  Si le mail échoue, la commande est quand même créée (statut « Non envoyé ») : bouton « Renvoyer le mail » dans la liste.
  Anti-doublon : une commande revalidée après coupure réseau n'est pas créée deux fois.
  À FAIRE PAR L'ADMIN M365 : ajouter la boîte administratif@novafit.fr aux boîtes autorisées de l'application Azure existante
  (Application Access Policy). Pas de nouvelle application ni de nouveau secret.
  Mise en service : coller Code.gs, exécuter autoriser(), nouvelle version du déploiement, envoyer les fichiers GitHub,
  puis vider le cache une fois (le service worker passe en v19).

PROTECTIONS D'ENVOI (arrêt d'urgence, plafonds, voyant)
-------------------------------------------------------
Objectif : empêcher qu'un compte piraté ne serve à envoyer des mails en masse.
1. Réglages en haut de Code.gs (à modifier puis redéployer : Déployer > Gérer les déploiements > crayon > Nouvelle version) :
   - PLAFOND_JOUR = 25               : mails par jour pour toute l'entreprise (bons + commandes d'achat)
   - PLAFOND_HEURE_PERSONNE = 2      : mails par heure et par personne
   - SEUIL_ALERTE_PERSONNE = 5       : au-delà, bandeau orange sur l'accueil de l'administrateur
   Un bon envoyé à plusieurs adresses compte pour un seul envoi. Un envoi qui échoue n'est pas compté.
   Les anciens codes communs comptent comme une seule « personne » (ex. « Code commun technicien »).
2. Arrêt d'urgence : page Utilisateurs, gros bouton rouge « Stop, on bloque tout » (deux appuis : demande + confirmation).
   Tant qu'il est actif, plus aucun mail de bon ni de commande ne part ; les bons restent gardés sur les téléphones et repartent après réactivation.
   Même bouton, devenu vert : « Réactiver les envois ».
3. Accueil de l'administrateur : rien quand tout va bien ; bandeau rouge « Envois bloqués » si l'arrêt est actif ; bandeau orange « Nom : N envois aujourd'hui » si quelqu'un dépasse le seuil.
4. Les contrôles sont faits côté script Google (impossible à contourner depuis le site GitHub). Le journal des envois (48 h) est dans les propriétés du script (JOURNAL_ENVOIS) ; l'état de l'arrêt dans ENVOIS_BLOQUES.
5. Ne concerne pas le script Jonction (inchangé).


NUMEROTATION DES BONS (règle du 13/11/2026)
-------------------------------------------
- Le numéro d'un bon est pris au clic sur « Valider et envoyer » (au moment où le script reçoit le bon) et reste attribué à ce bon, même si le mail échoue (panne Microsoft...). Le bon reste dans le Sheet, statut « écrit », et repart plus tard avec le même numéro, sans doublon.
- Ouvrir une commande, lire le PDF ou ouvrir la page du bon ne consomme JAMAIS de numéro (la page affiche seulement un numéro prévisionnel).
- Rien n'est pris si l'envoi est refusé avant écriture : arrêt d'urgence actif, plafond atteint, email invalide, bon sans bande, ou écriture impossible dans le Sheet (le compteur est alors rendu).
- Le numéro proposé = le plus grand entre le compteur Config!B1 et les numéros de la colonne E de Config, plus 1 : jamais de doublon.
- Seul cas où la page envoie toute seule : à l'ouverture de l'écran du bon, les bons DÉJÀ validés et restés en attente sur le téléphone sont renvoyés (même identifiant, donc même numéro).

NUMEROTATION DES COMMANDES FOURNISSEURS (contrôle du 13/11/2026)
  Même règle que les bons d'intervention : le numéro (ATELIER 26-0086...) est pris au clic sur « Envoyer » et jamais à l'ouverture
  du formulaire ni à l'aperçu PDF (le numéro affiché avant l'envoi n'est qu'indicatif).
  - Les étapes se font sous verrou : aucun doublon possible, même si deux personnes envoient en même temps.
  - Si une erreur survient avant l'écriture de la ligne (PDF, Drive) : rien n'est écrit, le compteur n'avance pas.
  - Si le mail échoue : la commande reste dans la liste avec son numéro et le PDF, statut « Non envoyé » ; le renvoi (bouton) réutilise
    le même numéro.
  - Une même commande envoyée deux fois (double clic, coupure réseau) n'est enregistrée qu'une fois (identifiant d'envoi).
  - Sécurité ajoutée (script 2026-11-13-g) : si une ligne est ajoutée à la main dans l'onglet Commandes avec un numéro plus élevé,
    le prochain numéro repart de ce numéro (pas de doublon). Colonne C : « 85 » ou « ATELIER 26-0085 » sont reconnus.
  - Au 1er janvier le compteur repart à 0001.

BON A SIGNER A DISTANCE (version du 15/11/2026, script 2026-11-15-b, site novafit-v44)
  Pour une intervention chez un client absent : le bon est rempli sur place, le client le signe ensuite en ligne.
  Droit : « Bon à signer à distance » (page Utilisateurs, un interrupteur par personne ; l'administrateur l'a d'office).
  Accueil : bouton « Bon à signer à distance » (sous Bon d'intervention), JAUNE tant qu'un bon n'est pas revenu signé (ou préparé et pas encore parti).
  Parcours :
    1. Bouton > « Nouveau bon à signer » > choix de la commande en cours (ou bon vierge) > le formulaire habituel, sans signature.
       La préparation peut se faire hors ligne sur le chantier : le bon est gardé sur l'appareil et le lien part dès que le réseau revient
       (bouton « Envoyer les liens maintenant » de la page Bons à signer, ou automatiquement).
    2. « Envoyer le lien de signature au client » : le numéro BI-AAAA-NNNN est réservé à ce moment, le client reçoit un mail (de info@novafit.fr)
       avec un lien personnel valable 7 jours (DISTANCE_JOURS en haut de Code.gs).
    3. Le client ouvre le lien (page signer.html, sans compte), vérifie le bon et ses photos, confirme son nom, signe et valide.
    4. À la validation : le bon entre dans l'onglet Bons, le PDF signé est rangé dans Drive, mail au client + copie technique@, la commande
       passe dans « Intervention faite ». Le lien ne marche plus.
  Suivi : page « Bons à signer » (bouton de l'accueil) : en attente (jaune), à relancer (rouge après DISTANCE_RAPPEL_JOURS = 2 jours sans signature,
    ou lien expiré), signés, annulés. Actions : renvoyer le lien (nouveau délai de 7 jours), annuler (le numéro reste attribué, trou visible).
  Où sont les données : onglet Config du Sheet des bons, colonnes D à O (idEnvoi, numéro, statut asigner/ecrit/mail/envoye/annule, lien secret,
    expiration, fichier Drive du bon, client, créé par, lien envoyé le, signé le, emails, adresse de la page). Le contenu du bon en attente est
    un fichier .json dans le dossier Drive « Bons à signer » (à côté de « Bons d'intervention ») ; il est supprimé une fois le bon signé.
  Protections : le mail du lien compte dans les limites d'envoi et l'arrêt d'urgence les bloque (le bon reste gardé sur l'appareil) ; la signature du
    client est refusée tant que l'arrêt d'urgence est actif (message « réessayez plus tard »). Le lien est un code de 48 caractères impossible à deviner,
    à usage unique ; la page client ne montre que ce bon (jamais l'adresse email) ; noindex.
  Signature = dessin + nom saisi + date/heure dans le Sheet (colonne « signé le » de Config) : preuve simple, pas une signature électronique certifiée.
  Si la signature échoue après l'écriture dans le Sheet (mail en panne) : statut « ecrit », le client peut réessayer avec le même lien, sans doublon.
  Déploiement : Code.gs (nouvelle version) + index.html, commandes.html, intervention.html, utilisateurs.html, shell.js, sw.js, et les 2 NOUVEAUX
    fichiers distance.html et signer.html. Puis cocher le droit pour les personnes concernées dans Utilisateurs.
  Adresse du lien envoyé au client : réglage URL_SIGNATURE en haut de Code.gs (ex : 'https://www.novafit.fr/intervention/signer.html').
    Vide : le lien reprend l'adresse du site depuis lequel le bon est envoyé (GitHub tant que tu travailles depuis GitHub). Renseigné : tous les liens
    utilisent cette adresse, la page signer.html (+ config.js, theme.css, theme.js, icon-192.png) doit alors être publiée à cet endroit.
